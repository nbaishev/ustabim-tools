# Требования безопасности

## Обязательные правила

- Браузер не вызывает n8n напрямую; приватные webhook доступны только серверным компонентам.
- Внутренние вызовы n8n подписываются отдельным секретом, включают метку времени и одноразовый идентификатор.
- `user_id`, `project_id` и роли из браузерного тела не считаются доказательством доступа.
- Сервер получает пользователя только из проверенной сессии Supabase и проверяет доступ к проекту для каждого запроса.
- RLS обязателен для всех пользовательских таблиц и проверяется отдельными тестами.
- Пользовательские файлы хранятся в приватных buckets; доступ выдаётся краткоживущей signed URL после авторизации.
- Service role, OpenAI API key и внутренние секреты не передаются в клиентский JavaScript. OpenAI API key хранится только в окружении n8n.
- n8n и workers возвращают наружу безопасный код ошибки, не раскрывая стек, запросы, ключи и внутренние адреса.
- Ограничиваются размер и тип файлов, частота запросов, число параллельных и повторных дорогих операций.
- PDF и IFC всегда считаются недоверенными: обработка изолируется, имеет лимиты памяти/времени и не исполняет вложенный код.
- Удаление проекта транзакционно закрывает доступ и ставит связанные объекты Storage и производные данные в идемпотентную очередь удаления.
- Логи содержат идентификаторы и технические метаданные, но не содержимое приватных документов, сообщений или signed URL без обоснованной необходимости.

## Основные угрозы и защита

| Угроза | Предлагаемая защита |
|---|---|
| Подмена `user_id` | Игнорировать клиентское значение; выводить пользователя из проверенного JWT/session cookie; передавать во внутренний контур только подписанный контекст. |
| Доступ к чужому `project_id` | Проверять членство/владение в серверном API и дублировать запрет политиками RLS; отвечать безопасным `NOT_FOUND` или `FORBIDDEN` по единой политике. |
| Утечка signed URL | Короткий TTL, HTTPS, выдача после проверки доступа, отсутствие URL в логах и аналитике; при инциденте — отзыв/ротация объекта. |
| Повторный запуск дорогой операции | Ключ идемпотентности, уникальное ограничение на активную попытку, rate limit, квоты и серверная блокировка в Redis. |
| Prompt injection из загруженного документа | Считать документ недоверенными данными, отделять инструкции системы от контента, ограничить набор tools, проверять выходную схему и требовать источники/ручную проверку. |
| Загрузка вредоносного файла | Проверка размера, расширения и MIME/signature, приватное хранение, изолированный worker без лишних прав, лимиты ресурсов и при необходимости антивирусное сканирование. |
| Утечка секретов через сообщение об ошибке | Централизованное преобразование исключений, публичные коды ошибок, редактирование логов и запрет передачи stack trace или ответов внутренних сервисов клиенту. |

## Доверительные границы

Интернет-клиент, загруженные документы и вывод модели недоверенны. Web server доверяет Supabase-сессии только после криптографической проверки. n8n доверяет запросу web server только после проверки подписи, времени и nonce. Workers доступны во внутренней сети и проверяют отдельный секрет, но всё равно валидируют входную схему и файл.
