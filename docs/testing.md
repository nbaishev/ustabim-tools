# Стратегия тестирования

> Каждый этап разработки должен иметь автоматическую или воспроизводимую ручную проверку.

## Виды тестов

### Unit-тесты

Проверяют чистую бизнес-логику, валидацию, переходы статусов, преобразование ошибок, вычислительные функции и сериализацию контрактов без сети и внешней базы.

### Интеграционные тесты

Проверяют API вместе с тестовой PostgreSQL/Storage, создание signed URL, подпись внутренних запросов, идемпотентность, сохранение результатов и обработку отказов n8n/workers.

### End-to-end тесты

Проверяют ключевые пользовательские пути в браузере: вход, создание проекта, загрузку файла, просмотр состояния задачи, чат и запуск калькулятора. Внешние платные API заменяются управляемыми заглушками.

### Тесты RLS

Для каждой пользовательской таблицы проверяются владелец, участник проекта, посторонний пользователь, анонимный запрос и service role. Отдельно проверяются INSERT/SELECT/UPDATE/DELETE и невозможность подменить владельца.

### Тесты n8n workflow

Workflow тестируются на фиксированных входах: успешный путь, таймаут, повторная доставка, ошибка модели/worker, недействительная подпись, ограничение квоты и восстановление после частичного выполнения. Экспорт workflow версионируется после появления реализации.

### Регрессионные тесты геологического анализа

Версионированный набор обезличенных PDF и ожидаемых структурированных результатов проверяет страницы-источники, числовые значения, единицы, таблицы, OCR, пропуски и уровень уверенности. Допуск сравнения задаётся для каждого числового поля; расхождения проходят ручной обзор.

### Тесты IFC

Небольшой набор валидных, повреждённых и больших IFC проверяет загрузку, дерево, свойства, количество элементов, ограничения ресурсов и отказоустойчивость viewer/worker. Геометрические эталоны хранятся отдельно от базы.

### Тесты калькуляторов

Каждый алгоритм имеет эталонные примеры, граничные и недопустимые входы, проверку единиц и числового допуска. Результат теста фиксирует версию алгоритма и исключает незаметное изменение старых расчётов.

### Security-тесты

Проверяются IDOR между проектами, RLS, подмена сессии, истёкшие signed URL, replay внутренних запросов, rate limit, вредоносные PDF/IFC, prompt injection, утечки секретов и приватных данных в ответах и логах.

## Шаблон проверки задачи

```text
Цель:
Предусловия:
Команды:
Шаги ручной проверки:
Ожидаемый результат:
Проверка ошибки:
Изменённые файлы:
```

В описании задачи должны быть воспроизводимые данные и точные ожидаемые результаты. Если автоматическая проверка временно невозможна, причина и ручной сценарий фиксируются явно.

## Текущие проверки frontend-прототипа

Команды выполняются из корня npm workspace:

```bash
npm run lint
npm run typecheck
npm run test
npm run build
npm run test:e2e
```

Vitest и React Testing Library проверяют `ToolCard`, регистрацию с совпадением паролей, переход на нейтральный экран, безопасное отображение rate limit, email/password вход, переход на нейтральный recovery-экран, фиксированные callback URL, маршрутно-зависимую навигацию кабинета, валидацию расширения/размера/STEP-заголовка IFC, преобразование IFC-свойств и пространственного дерева, `updateUser`, завершение recovery-сессии и очистку паролей. Отдельные unit-тесты проверяют Supabase-конфигурацию и health-check. Playwright в Chromium проверяет публичные маршруты, отсутствие Google OAuth, локальную валидацию регистрации, экраны проверки почты, безопасный callback, redirect с `/app`, `/app/profile` и `/app/ifc`, публичную recovery-форму и запрет прямого доступа к `/reset-password`. Реальные письма, успешные signup/recovery flows, Auth-данные профиля, визуальная загрузка настоящего IFC, raycast-выбор, измерения и разрезы проверяются вручную. Перед первым E2E-запуском браузер устанавливается командой `npx playwright install chromium`.

Для запуска и сборки нужен `apps/web/.env.local`, созданный из корневого `.env.example`. `NEXT_PUBLIC_APP_NAME` и `NEXT_PUBLIC_APP_URL` обязательны. Пустая пара Supabase-переменных разрешена для автономной разработки; если указана одна из них, конфигурация считается ошибочной. Реальный внешний health-check выполняется вручную только с credentials отдельного тестового проекта.
